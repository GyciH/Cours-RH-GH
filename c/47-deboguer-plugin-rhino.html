Le concept

Déboguer un plugin dans Rhino

Un plugin Grasshopper ne tourne pas seul : il vit dans Rhino. Le déboguer, c'est donc faire démarrer Rhino par Visual Studio, sur le dernier build, et pouvoir regarder dedans : un point d'arrêt quand on est devant l'écran, un volet de diagnostic quand on veut voir l'état en continu.

45 min de lecture et de QCM Prérequis · 04, 05, 07 et 27 Exemples · launchSettings.json (Cuttlefish), SnapSet.Conception.csproj (SnapSet), MagpieDebugPanel.cs (Magpie)

L'idée en une phrase

Trois questions à régler une fois pour toutes : quel Rhino démarre et sur quel moteur .NET, d'où il charge ton plugin, et comment tu vois ce qui se passe quand tu ne peux pas t'arrêter dans le code.

L'analogie

Le banc moteur d'un garage. On ne teste pas un moteur posé sur l'établi : on le monte sur le banc, on branche les capteurs, et l'on regarde les cadrans tourner pendant qu'il marche.

À la fin, tu sais

  1. lire un profil de lancement Rhino dans launchSettings.json ;
  2. choisir entre /netcore et /netfx ;
  3. dire ce qui se remplace Rhino ouvert, et ce qui ne se remplace pas ;
  4. construire un volet de diagnostic, et le garder hors des versions publiées.
À retenir Avant de poser un point d'arrêt, demande-toi quel fichier Rhino a chargé. La moitié des « mon correctif ne marche pas » viennent d'un Rhino qui tourne encore sur l'ancien build : SnapSet a même une erreur de build dédiée à ce cas (ATC911).

Schéma 1 · Lancer Rhino depuis Visual Studio

Un profil de lancement

Le fichier Properties/launchSettings.json décrit ce que fait F5. Pour un plugin, on ne lance pas son projet, qui n'est pas un programme : on lance Rhino.exe, avec des arguments, et Visual Studio s'attache à lui.

Cuttlefish · Properties/launchSettings.json · 3–17"Rhino 8 - netcore": { "commandName": "Executable", "executablePath": "D:\\programme\\Rhino\\System\\Rhino.exe", "commandLineArgs": "/netcore /runscript=\"_Grasshopper\"", "environmentVariables": { "RHINO_PACKAGE_DIRS": "$(ProjectDir)$(OutputPath)\\" } }, "Rhino 8 - netfx": { "commandName": "Executable", "executablePath": "D:\\programme\\Rhino\\System\\Rhino.exe", "commandLineArgs": "/netfx /runscript=\"_Grasshopper\"", …

/netcore ou /netfx

Rhino 8 sait tourner sur .NET 7 (/netcore) ou sur le .NET Framework 4.8 (/netfx). Cuttlefish ne cible que net48 (Cuttlefish.csproj, ligne 10) : son profil netfx fait tourner Rhino sur le moteur pour lequel il est compilé.

RHINO_PACKAGE_DIRS

Cette variable d'environnement donne à Rhino un dossier de plus où chercher des plugins : ici, le dossier de sortie du build. Rhino charge donc le .gha que tu viens de compiler, sans rien copier nulle part.

Piège réel Un chemin propre à une machine. D:\programme\Rhino\System\Rhino.exe n'existe que sur ton poste ; ailleurs, F5 échoue avant même de démarrer. Le profil « Rhino 7 », lui, garde le chemin d'installation par défaut (C:\Program Files\Rhino 7). Un profil se versionne, mais se relit sur chaque nouveau poste.

Schéma 2 · Copier, Rhino ouvert ou fermé

Ce qui se remplace, et ce qui est verrouillé

SnapSet fait l'inverse : après chaque build, une cible MSBuild copie le plugin dans %APPDATA%\Grasshopper\Libraries, où tout Rhino le trouve. Mais les deux fichiers ne se comportent pas pareil quand Rhino est ouvert.

SnapSet · src/SnapSet.Conception/SnapSet.Conception.csproj · 61–65 et 83–85DÉPLOIEMENT : le .gha se remplace même Rhino ouvert (Grasshopper le charge en mémoire), la DLL d'exécution SnapSet.Constituants.dll non (assembly chargé depuis le disque, donc verrouillé). Copier l'un sans l'autre donnerait un déploiement à moitié périmé SANS RIEN DIRE : la copie de la DLL échoue donc franchement (ATC911). Ferme Rhino avant de déployer. … <Error Condition="'@(ConstituantsCopie)' == ''" Code="ATC911" Text="… Ferme Rhino et relance le build." />

Construire sans déployer

Rhino ouvert, on veut quand même savoir si ça compile : dotnet build SnapSet.sln -p:DeployerVersLibraries=false (README, ligne 44). La cible de copie a pour condition cette propriété (ligne 70) et ne s'exécute pas.

Échouer franchement

Une copie ratée est d'abord tolérée (ContinueOnError), puis on regarde si la DLL est bien passée. Si non, <Error> arrête le build avec un message qui dit quoi faire. Un échec bruyant vaut mieux qu'un succès trompeur.

Piège réel Le déploiement à moitié périmé. Le .gha neuf est copié, la DLL ancienne reste : Rhino redémarré charge un plugin qui appelle des types d'avant le correctif. Rien ne plante tout de suite, et l'on cherche un bogue déjà corrigé. C'est ce que l'erreur ATC911 empêche.

Schéma 3 · Voir sans s'arrêter

Un composant de diagnostic

Un point d'arrêt fige tout ; or certains bogues ne se voient qu'en marche : un compteur de tentatives, un temps écoulé, un verdict qui change. Magpie a donc un composant « Magpie - Debug » qui expose l'état de la session sur ses sorties, à brancher sur des Panels.

Magpie · plugin/Dev/MagpieDev.csproj · 3–8 et 19–22LA VERSION DEV : MagpieDev.gha. Le seul volet de debug (« Magpie - Debug »), qui montre l'état de la session et la réponse attendue. Pour le poste de développement uniquement : elle N'A PAS VOCATION À ÊTRE RENDUE PUBLIQUE, ni jointe aux releases. … <Compile Include="MagpieDevInfo.cs" /> <Compile Include="..\Admin\MagpieDebugPanel.cs" Link="Admin\MagpieDebugPanel.cs" />

Un binaire à part

Le volet n'est dans aucun .gha livré : il a son propre projet, qui ne compile que lui (EnableDefaultCompileItems à false). Il s'installe à côté de l'Apprenant et observe la même session, grâce au Core partagé (cours 27).

Les deux autres voix

RhinoApp.WriteLine écrit dans la ligne de commande de Rhino, AddRuntimeMessage colore le composant en orange ou en rouge avec un message au survol. Tes trois dépôts y ont recours plus de soixante-dix fois : c'est le débogage du quotidien.

Piège réel Livrer le diagnostic. Le volet montre la réponse attendue, et le message du checker nomme le premier élément fautif : « ce texte RÉVÈLE la réponse attendue » (GenericChecker.cs, lignes 306–310). Dans un .gha d'apprenant, ce serait le corrigé offert. D'où MagpieDev.gha, jamais publié.

Dans tes projets

MagpieDebugPanel : se tenir à jour

Le volet n'a aucune entrée : rien ne le ferait recalculer. Il s'abonne donc lui-même aux changements de la session, et ajoute une minuterie d'une seconde pour le temps écoulé. Tout ce qu'il ouvre en arrivant, il le referme en partant.

Pourquoi ScheduleSolution La minuterie peut sonner pendant que Grasshopper calcule. Expirer un composant en pleine solution n'est pas permis ; ScheduleSolution(1, …) demande une solution dans une milliseconde et appelle le rappel juste avant, au moment où expirer est sûr. Les éditeurs de Magpie l'emploient aussi (MagpieExerciseEditor.cs, ligne 405).

Glossaire

Profil de lancement
Ce que fait F5 : quel exécutable, quels arguments, quelles variables.
Point d'arrêt
Une ligne où le débogueur suspend le programme pour l'inspecter.
Fichier verrouillé
Un fichier ouvert par un programme, que Windows refuse de remplacer.
Libraries
%APPDATA%\Grasshopper\Libraries : le dossier où Grasshopper cherche ses plugins.
Volet de diagnostic
Un composant qui expose un état interne, pour le développeur seul.
