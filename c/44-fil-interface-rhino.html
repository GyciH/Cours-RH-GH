Le concept

Le fil d'interface de Rhino

Tout ce que tu vois bouger dans Grasshopper passe par un seul fil d'exécution, qui traite une file de messages l'un après l'autre : un clic, une peinture, un menu. Tes composants n'ont pas de Task.Run ni d'async : leur vrai outil est de remettre à plus tard, sur ce même fil, ce qui ne doit pas se faire au milieu d'un geste.

45 min de lecture et de QCM Prérequis · 11, 21, 27 et 43 Exemples · CapsuleExecution.cs, ComposantDepart.cs (SnapSet), ChargeurCore.cs (Magpie)

L'idée en une phrase

Pendant que ton code traite un message, aucun autre ne passe : ni peinture, ni clic. On garde donc chaque traitement court, et ce qui peut attendre, on le poste à la fin de la file avec BeginInvoke.

L'analogie

Un seul guichet, une seule file. Un client qui ouvre un long dossier au guichet bloque tout le monde ; le bon guichetier lui dit « reprenez un ticket », et le traite à son tour.

À la fin, tu sais

  1. dire ce qu'est la boucle de messages et ce qui la fige ;
  2. ouvrir une fenêtre après un clic, par BeginInvoke ;
  3. choisir entre Invalidate et Refresh ;
  4. attendre le repos de Rhino, ou protéger un état partagé par un verrou.
À retenir BeginInvoke ne crée aucun fil : il dépose l'action dans la file du contrôle, et le même fil l'exécutera après le message en cours. Dans Grasshopper 1, la solution elle-même tourne sur ce fil : un composant lent fige le canvas pour la même raison.

Schéma 1 · Une fenêtre après le clic

Ne pas ouvrir de fenêtre au milieu d'un geste

Un menu, un sélecteur de couleur ou une boîte de dialogue ont leur propre boucle : ils ne rendent la main qu'à leur fermeture. Ouverts dans RespondToMouseDown, ils suspendraient le geste de Grasshopper en plein milieu. SnapSet les ouvre donc après, par canvas.BeginInvoke.

SnapSet · Execution/CapsuleExecution.cs · 683–687 et 1075–1085if (geste.Action == ActionListe.OuvrirMenu) { var point = e.ControlLocation; canvas.BeginInvoke(new Action(() => Proteger(() => l.MontrerMenu(canvas, point)))); return GH_ObjectResponse.Handled; } … private void Proteger(Action action) { try { action(); } catch (Exception ex) { Signaler(ex); } // écrit dans la ligne de commande de Rhino }

Copier le point avant de partir

var point = e.ControlLocation; est lu maintenant. L'action postée s'exécutera plus tard, quand l'événement de souris ne voudra plus rien dire : elle n'emporte que ce qu'on lui a donné.

Pourquoi Proteger

Une exception dans une action postée ne remonte plus à ton gestionnaire de souris, déjà terminé : elle tomberait dans la boucle de messages de Rhino. Proteger l'attrape et l'écrit dans la ligne de commande.

Piège réel Garder la capture de la souris après une exception. Une feuille qui a capté l'enfoncement doit la rendre dans un finally ; sinon, une exception fige le canvas, qui attend un relâchement qui ne viendra plus (CONTRAT-CONTENEUR.md, C6, ligne 307).

Schéma 2 · Peindre maintenant, ou bientôt

Invalidate n'est pas Refresh

Invalidate marque le contrôle comme « à repeindre » : la peinture viendra par la file, une seule fois même si on l'a demandée dix fois. Refresh peint tout de suite, au milieu de ce que tu es en train de faire.

SnapSet · Appartenance/RegistreDocument.cs · 502–506// Les constituants que pose le composant de départ arrivent déjà rangés (PoserLeDepart) : ni // adoption, ni réduction de sélection — et SURTOUT PAS de RedrawCanvas : Instances.RedrawCanvas est un // Control.Refresh SYNCHRONE (DLL) ; peindre la Ligne avant que ses Colonnes soient ajoutées déclencherait // SignalerRendu, dont la purge viderait sa liste. PoserLeDepart redessine à la fin. if (_poseEnCours) return;

Le cas courant : Invalidate

Un bouton enfoncé change d'aspect : canvas.Invalidate() (CapsuleExecution.cs, ligne 673), et l'on rend la main. La peinture passera dès que la file sera libre, avec l'état complet.

Le nom trompe

Instances.RedrawCanvas() a l'air d'une demande ; c'est en fait un Refresh. SnapSet l'appelle à la fin d'une opération, jamais au milieu d'une construction en plusieurs temps.

Piège réel Peindre un état à moitié construit. Pendant que le composant de départ pose une Ligne puis ses Colonnes, un Refresh peindrait la Ligne seule, et sa purge viderait sa liste de membres. D'où le drapeau _poseEnCours et un seul redessin à la fin.

Schéma 3 · Sans canvas, et à plusieurs fils

Attendre le repos, ou poser un verrou

Sans canvas, il n'y a pas de contrôle à qui poster : on attend alors que Rhino n'ait plus rien à faire, avec l'événement RhinoApp.Idle. Et dans le rare code qui peut être appelé depuis plusieurs fils, on protège l'état partagé par un lock.

SnapSet · Depart/ComposantDepart.cs · 116–132private static void Differer(Action action) { var canvas = Instances.ActiveCanvas; if (canvas != null && canvas.IsHandleCreated) { canvas.BeginInvoke(action); return; } EventHandler auRepos = null; auRepos = (s, e) => { Rhino.RhinoApp.Idle -= auRepos; action(); }; Rhino.RhinoApp.Idle += auRepos; }

Le gestionnaire qui se retire

Idle se lève à chaque moment de repos, très souvent. Le gestionnaire se désabonne donc lui-même avant d'agir : il ne court qu'une fois. Il est déclaré à null d'abord pour pouvoir se nommer dans son propre corps.

Un verrou pour un chargeur

AssemblyResolve se lève sur le fil qui a besoin de la bibliothèque, quel qu'il soit. ChargeurCore entoure donc son branchement et sa résolution d'un lock (Verrou) (lignes 63, 76, 99) : un seul Magpie.Core chargé, quoi qu'il arrive.

Piège courant Oublier le -=. Un gestionnaire d'Idle qui ne se retire pas rejoue son action à chaque repos de Rhino, plusieurs fois par seconde, jusqu'à la fermeture. Le symptôme : un composant qui « se remplace » sans fin, ou un Rhino qui chauffe au repos.

Glossaire

Fil d'exécution
Une suite d'instructions exécutées l'une après l'autre (thread).
Boucle de messages
La boucle du fil d'interface qui traite clics, peintures et minuteries un par un.
BeginInvoke
Poster une action dans la file d'un contrôle, sans l'attendre.
Idle
L'événement de Rhino levé quand la file est vide.
Verrou
lock : une seule exécution à la fois dans le bloc protégé.
